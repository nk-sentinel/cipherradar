# ADR-038: Installer Checksum Verification

**Status:** Accepted
**Date:** 2026-05-18
**Supersedes:** —

## Context

`cradar install-tools` downloads OpenGrep (and YARA-X) from GitHub
release assets over HTTPS. Prior to rc2 the downloaded binary was
written to disk and executed without any integrity check beyond the
HTTPS TLS handshake. A compromised mirror, MITM at the time of a TLS
break, or a server-side asset swap could install an attacker-controlled
binary that cradar would happily run on every subsequent scan.

## Decision

Verify SHA-256 of every downloaded OpenGrep binary against the
`digest` field GitHub's Releases API publishes for each release asset
(format `"sha256:<hex>"`). On mismatch, delete the temp file and
return an error (mapped to exit 4 — `ExitToolError`). HTTPS is required
— `http://` URLs are refused at the installer layer for both the API
and the binary download.

Implementation:
- `cli/internal/tools/checksum.go` — `VerifySHA256(path, expected)`:
  streaming SHA-256 with case-insensitive hex comparison.
- `cli/internal/tools/installer.go` — `fetchReleaseAsset` GETs
  `https://api.github.com/repos/opengrep/opengrep/releases/tags/<ver>`,
  finds the asset by name, parses `digest`. `downloadToTemp` streams
  the binary into a temp file in the destination directory.
  `InstallOpenGrep` composes: fetch digest → download to temp →
  VerifySHA256 → chmod 0755 → atomic rename.
- `requireHTTPS` rejects non-HTTPS URLs.

## Alternatives considered

1. **Sidecar `.sha256` files alongside each binary asset.** Original
   plan. Rejected because OpenGrep v1.16.5 does not publish any
   sidecar files (confirmed via 404 on `.sha256`, `.sha256sum`, and
   `.SHA256`; release notes contain no digests; no release-level
   SHASUMS file). Would require upstream changes.
2. **Sigstore signatures (`.sig` + `.cert`).** Strongest option —
   verifies publisher identity, not just bit-integrity, and aligns
   with ADR-020 (CBOM signing). OpenGrep does publish Sigstore
   sidecars for some releases. Deferred because it requires either
   a `sigstore-go` dependency or shelling out to `cosign`, both of
   which are heavier than this rc2 scope. Revisit when YARA-X
   verification lands.
3. **Embedded SHA-256 constants per platform.** Strongest threat
   model — offline verification, attacker who compromises GitHub
   today can't bypass our hardcoded value. Trade-off: every version
   bump requires updating four constants and manual verification at
   PR time. Acceptable for the existing pinned version model but
   higher maintenance overhead.
4. **GPG signature verification.** Same publisher-dependency problem
   as Sigstore without the keyless-signing UX. OpenGrep does not
   publish GPG signatures today.

## Trust anchor

The GitHub Releases API response, authenticated via GitHub's TLS.
GitHub computes the `digest` field server-side from the published
asset, so this verifies bit-integrity of the asset as GitHub stored
it. Weaker than offline-pinned constants (an attacker who fully
compromises GitHub can serve any pair `(binary, matching digest)`)
but strictly better than no verification — it closes the CDN-cache
poisoning and repository-infrastructure-compromise-without-API-
regeneration failure modes.

## Consequences

- Every fresh OpenGrep install now requires two HTTPS GETs instead
  of one (API + binary). Bounded overhead (~50ms wall).
- API rate-limited to 60 requests/hour unauthenticated, which is
  fine for `install-tools` (run rarely, never in tight loops).
- Mismatch produces a hard exit (4) rather than installing an
  unverified binary.
- YARA-X path unchanged in rc2 — still uses the legacy unverified
  tarball download. Sigstore verification (alternative 2) is the
  natural follow-up that would cover both tools.
